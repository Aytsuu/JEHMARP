## Incident and diagnosis

The `Deploy Staging` workflow failed at **Apply pending staging migrations**
with:

```text
Remote migration versions not found in local migrations directory.
```

This is a deterministic migration-history mismatch, not a database-network
failure. The managed staging project still records the pre-cutover historical
migration versions, while this checkout now deliberately contains exactly one
active baseline migration:

```text
supabase/migrations/20260802000000_baseline_schema.sql
```

The previous migration files are preserved at:

```text
supabase/_archived_migrations/20260802_checkpoint_prebaseline/
```

`supabase db push` compares the local directory with
`supabase_migrations.schema_migrations`; it must refuse to push when remote
versions have no corresponding local files. Retrying the same command five
times, or retrying through the pooler, cannot resolve a ledger mismatch.

## Objective

Make the staging deployment path fail fast with a precise baseline-reconciliation
instruction instead of retrying a known non-transient error. Reconcile **staging
only** through the existing guarded manual workflow, then prove that the normal
staging deployment succeeds. Do not change production state.

## Decision and execution order

The existing `Reconcile Supabase Baseline` workflow is the immediate,
staging-only remediation for the failed deployment. It must be executed as the
manual operational sequence in step 4 below before rerunning `Deploy Staging`.
No repository code change is required to make the metadata reconciliation
possible.

The pre-push guard in steps 1-3 is follow-up hardening: it improves the failure
message and prevents wasted retries if a future environment has not yet been
reconciled. Implement it in the same change set only if it does not delay the
reviewed staging reconciliation. Never use it to automate repair.

## Mandatory safety boundaries

1. Do **not** add `supabase migration repair` to `deploy-staging.yml`,
   `supabase-db-push-remote.sh`, or any automatically triggered workflow.
2. Do **not** run `supabase db push` against staging while its ledger still
   contains the archived history.
3. Do **not** run seed SQL, reset the managed project, or apply the baseline
   schema SQL to staging. The managed schema is already represented by that
   baseline; this cutover changes migration metadata only.
4. Do **not** run the reconciliation workflow against production in this task.
5. Preserve production GitHub Environment protection and the existing manual
   acknowledgement requirements.

## Execution plan

### 1. Add a pre-push ledger guard (repository implementation)

Add a small, testable Bash helper under `.github/scripts/` (name it for its
purpose, for example `assert-supabase-baseline-ledger-state.sh`). It must:

- accept the existing linked-project or pooler-URL connection mode used by the
  deployment workflow;
- collect the remote migration versions using `supabase migration list`;
- derive the one active baseline version from `supabase/migrations/` and the
  archived historical versions from
  `supabase/_archived_migrations/20260802_checkpoint_prebaseline/`;
- allow the normal `db push` path only when the remote ledger already contains
  exactly the active baseline version and no historical versions;
- exit non-zero **before** `db push` when the remote ledger exactly matches the
  archived checkpoint, with an actionable message naming:
  `Reconcile Supabase Baseline`, target `staging`, version `20260802000000`,
  and `execution_mode=plan-only` as the next action;
- fail closed with a distinct drift message when the remote ledger matches
  neither the archived checkpoint nor the single-baseline state. Print only
  migration versions—never URLs, passwords, access tokens, or secrets.

Use the CLI's ASCII `|` table output defensively. Do not duplicate the old
mojibake box-drawing-column parser.

### 2. Wire the guard into the staging deployment workflow

In `.github/workflows/deploy-staging.yml`, add a named step immediately before
**Gate pending migrations for Expand-only auto-push** / **Apply pending staging
migrations**. Reuse the same linked-or-pooler credentials path used by nearby
migration-list steps.

The guard must run before `validate-migration-phase-metadata.sh` and before
`.github/scripts/supabase-db-push-remote.sh`, so the job produces one clear
failure and does not spend five retries on a permanent mismatch. Keep the
existing normal migration path unchanged after the guard passes.

Do not weaken the Expand-only gate and do not use `continue-on-error` for this
guard.

### 3. Test the new failure classification before implementation is considered done

Add focused shell regression tests under `.github/scripts/tests/` covering at
least these fixtures:

1. remote versions equal the archived checkpoint -> reject before push and show
   the staging `plan-only` instruction;
2. remote versions equal only `20260802000000` -> permit the standard deploy
   path;
3. empty, mixed, or unexpected remote versions -> fail closed as ledger drift;
4. linked and pooler invocation arguments select the correct migration-list
   mode;
5. no secret value is printed in any failure message.

Run the new test plus the existing
`.github/scripts/tests/reconcile-supabase-baseline-workflow.test.sh` in Linux
Docker, run `git diff --check`, and validate workflow syntax with `actionlint`
or the repository's equivalent.

### 4. Immediate stage-only operational reconciliation (manual; do not automate)

Dispatch the existing **Reconcile Supabase Baseline** workflow against `staging`:

```text
target: staging
expected_baseline_version: 20260802000000
confirmation_token: I_UNDERSTAND_THIS_IS_A_METADATA_ONLY_RECONCILIATION
execution_mode: plan-only
```

Review the uploaded artifact. It must show that staging's remote versions
exactly match the archived checkpoint and that the checkout has one pending
baseline. If it reports any drift, stop and report it here—do not repair it.

Only after a successful reviewed preflight, run a separately approved staging
dispatch with:

```text
execution_mode: execute-ledger-repair
execute_confirmation: APPLY_METADATA_ONLY
```

This is metadata-only: mark the archived remote versions reverted, then mark
`20260802000000` applied. It must not run `db push` or schema/seed SQL.

### 5. Verification and handoff

After the staging metadata reconciliation:

1. Confirm `supabase migration list` records exactly the single baseline for
   both local and remote columns.
2. Run the normal `Deploy Staging` pipeline again. Its local database tests,
   guard, migration gate, and remote `db push` step must all pass; `db push`
   should have no pending SQL to apply.
3. Confirm the Worker deployment and staging smoke tests pass.
4. Attach the reconciliation artifact and successful staging deployment URL in
   the reply below.
5. Do not touch production. Production requires its own fresh ledger audit,
   protected-environment approval, and a separately authorized staging-proven
   reconciliation.

## Acceptance criteria

- A historical-ledger staging project fails at the new pre-push guard with a
  concise, actionable manual-reconciliation instruction—not after retrying
  `db push`.
- A baseline-reconciled staging project continues through the existing
  Expand-only gate and normal deployment flow.
- All new guard tests and existing reconciliation workflow tests pass.
- The staging project is reconciled only after a reviewed `plan-only` artifact.
- No managed production database schema, data, seed, or migration-history
  records are changed.

### Observed failure

The `Validate dev to main` job **Scan changed migrations for high-risk SQL**
fails before it can inspect SQL:

```text
Migration file not found: /home/runner/work/JEHMARP/JEHMARP/
supabase/migrations/20260712180918_baseline_schema.sql
```

That file was deliberately removed from the active migrations directory by the
history-compaction checkpoint and preserved under
`supabase/_archived_migrations/20260802_checkpoint_prebaseline/`. The current
diff against `main` contains it with status `D`; it is not a candidate
migration file in the PR checkout.

The defect is in diff-file selection, not in the baseline SQL or the managed
database. `validate-expand-migration-sql.sh --diff-base origin/main` currently
uses unfiltered `git diff --name-only` and then errors when it attempts to
open a deleted path. The same unsafe selection exists in
`validate-migration-phase-metadata.sh` and in the inline `head`/`grep` scans
inside both `validate-production-pr.yml` and `supabase-migration-safety.yml`.

### Required implementation

1. Introduce one reusable way to derive **current scanable migration files**
   for a diff range. It must include only added or modified files whose
   post-image exists under `supabase/migrations/`; it must exclude deleted
   historical paths. Preserve a separate all-status changed-path list only for
   audit/reporting if needed.

   Use a status-aware Git query such as `--diff-filter=ACMR` (with explicit
   rename/copy detection) and perform an existence check before `head`, `grep`, or
   opening the file. Never silently treat a missing current candidate as an
   empty SQL file.

2. Apply the same current-file selector consistently to:

   - `.github/scripts/validate-expand-migration-sql.sh` when `--diff-base` is
     used;
   - `.github/scripts/validate-migration-phase-metadata.sh` when `--diff-base`
     is used;
   - `.github/workflows/validate-production-pr.yml` high-risk inline scans;
   - `.github/workflows/supabase-migration-safety.yml` high-risk inline scans.

   Do not remove the audit visibility of the 70 deletions; only prevent deleted
   files from being scanned as SQL in the candidate checkout.

3. Keep new active migration policy strict. The newly added
   `20260802000000_baseline_schema.sql` must not become an unreviewed bypass
   merely because deleted files are excluded. Choose and document one narrow,
   tested approach:

   - preferred: add an explicit baseline-compaction marker/header and extend
     the metadata validator to recognize this one-time migration type only
     when the checkout has exactly one active baseline and the archived
     checkpoint is present; or
   - retain the baseline as a legacy/no-phase file but require the PR's
     `migration-reviewed` label for its high-risk SQL review, while changing
     the newly-added metadata gate to allow only this verified compaction
     shape.

   The exception must be impossible for ordinary future migrations to claim.
   Every later migration still requires normal complete Expand or Contract
   metadata. Do not label the schema dump `expand` just to pass the scanner:
   it contains historical destructive statements and is not an incremental
   Expand migration.

4. Ensure all multiline file lists are safe when empty. Do not feed an empty
   string into `xargs grep`; do not call `head` on a deleted path. Keep
   `set -euo pipefail` enabled and return a useful error if a status-selected
   added/modified path unexpectedly disappears.

### Required regression coverage

Extend the shell tests and workflow-static tests before changing production PR
behavior. Cover at least:

1. a diff containing `D old.sql` and `A new.sql` selects only `new.sql` for
   SQL and metadata validation;
2. a deleted migration alone produces a clean, explicit no-current-files
   result rather than `Migration file not found`;
3. a modified current migration is still scanned and destructive Expand SQL is
   still rejected;
4. a newly added ordinary migration without required metadata still fails;
5. the verified history-compaction baseline follows only the selected narrow
   exception and remains subject to reviewed/high-risk policy;
6. both `validate-production-pr.yml` and `supabase-migration-safety.yml` use
   the current-file list for every `head`/`grep`/`xargs` operation;
7. workflow scans never read from `supabase/_archived_migrations/` as active
   migration SQL.

Run the focused shell suites in Linux Docker, including:

```text

.github/scripts/tests/validate-migration-phase-metadata.test.sh
.github/scripts/tests/validate-production-pr-workflow.test.sh
```

Also run the full relevant workflow-script test set, `git diff --check`, and
`actionlint` for the modified workflows. Then re-run the `dev -> main` PR
pipeline. The high-risk-scan job must report the historical deletions as audit
context if desired, but it must no longer attempt to open them.
